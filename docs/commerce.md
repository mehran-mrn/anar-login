# Anar Toolkit 0.7.0

The WordPress.org package is built with `python tools/package.py --output /absolute/path/anar-toolkit-0.7.0.zip`. Its top-level folder and gettext domain are `anar-toolkit`; the review team confirmed this slug on 30 October 2026. The main PHP filename, namespace, login REST namespace, user identities and login option keys are intentionally preserved for existing integrations.

Both package profiles include Kavenegar, Meli Payamak, IPPanel, Panelchi, Faraz SMS and SMS.ir, plus custom HTTP. Panelchi uses its approved-pattern POST API with Bearer authentication; the default source number is 10001. Commerce patterns and variable mappings are configured separately from login patterns. Faraz uses IPPanel infrastructure under the disclosed Faraz service agreement. See `readme.txt` and `services.txt` for the endpoint inventory and verified service-policy links and limitations.

Do not activate the old `anar-login` folder and the new `anar-toolkit` folder simultaneously. Deactivate the old pre-release copy, install the new ZIP, and activate it. Existing `anar_login_settings`, `_anar_phone` and Google identities are retained. Commerce settings live separately in `anar_toolkit_commerce` so the login settings form cannot silently reset them.

## Modules

All new modules default off. The Commerce toolkit submenu is available without WooCommerce so settings and privacy tools remain accessible. Runtime commerce hooks need WooCommerce; the existing login feature remains independently usable.

Payment notices subscribe to `woocommerce_payment_complete`. `is_paid()`, a paid timestamp and a positive total are checked both when enqueuing and when processing. Order creation, a thank-you page view, pending payment and simply selecting COD do not send notices. A unique queue key plus a WooCommerce CRUD metadata flag prevents repeated gateway callbacks from duplicating the notifications. Manual status changes alone do not represent this event.

The customer saves an explicit reminder preference using the classic cart/checkout form or `[anar_cart_reminders]` placed beside a Cart/Checkout block. A session-bound nonce protects the save endpoint. No reminder row is created merely by typing a phone at checkout or receiving an OTP. Only standard product IDs, variation attributes and quantities are stored. Add-on/bundle/subscription/cart-extension metadata is not recreated. Cart and checkout blocks do not have a native login or reminder React component; use the separate reminder shortcode.

Stages are absolute minutes since the last saved cart modification. Disabled stages are zero. Stages are ordered and clamped below the link expiry. Each stage has its own template and parameters. The worker paginates active carts so more than 100 carts do not starve newer carts. It rechecks consent, current order state, inactivity, link expiry, quiet hours and a per-phone rolling 24-hour cap. A payment/cancellation/opt-out stops pending recovery. Disabling a module prevents its queue from sending.

Recovery uses a phone-bound six-digit code, not a bearer recovery link. `[anar_recover_cart]` is also rendered automatically on classic cart/checkout, including empty carts. Codes are stored as keyed hashes in the existing OTP table under a separate `recovery` channel. Contacts bind the challenge ID to the cart ID. Code validity is configurable from 5 to 1440 minutes (30 by default), with five atomic attempts, single-use consumption and independent per-IP/per-phone guess budgets. Verification never creates/logs in a user. Explicit new-code requests are rate limited, queued using the first recovery template, and respond identically for unknown, suppressed and eligible numbers. They are user-initiated verification messages, so reminder quiet hours/daily caps do not apply; resend/hourly security limits do.

Only the opt-out URL remains signed. It uses an action-specific 160-bit HMAC and opens a confirmation page; a GET cannot unsubscribe. SMS includes `{code}` and `{recovery_page}`, the public entry-page URL. The URL itself carries no code/account capability. The configured page defaults to WooCommerce cart; custom pages must contain `[anar_recover_cart]`. No bearer `recover` URL is generated or accepted. A valid recovery code navigates a pending order to WooCommerce's own pay URL or restores saved products at current prices/stock. Standard WooCommerce order checks still apply. Recovery deliberately replaces the current cart after the customer presses the labelled verification/continue button. Failure restores previous contents/coupons and a new code can be requested.

## Sending

Commerce uses independent provider template IDs; it never reuses the OTP template. Parameters are explicit `name={placeholder}` lines. Kavenegar accepts the documented token names and limits each value to 100 Unicode characters with the allowed spaces. Very long site URLs may exceed this limit: the job fails before HTTP rather than reporting acceptance. The short unsubscribe link is created locally; recovery uses the six-digit code and no recovery URL. Meli Payamak values are sent in mapping order, separated by semicolons. Custom transport requires `{message}`. Configure and test an approved template for each purpose at the provider.

Action Scheduler runs the queue when available, otherwise a one-minute WP-Cron interval is registered. Scheduler execution still depends on runner/traffic/server cron. One atomic compare-and-swap lease excludes concurrent workers. Each job also requires an atomic pending-to-running claim. Each run processes at most ten due jobs, stopping its loop after about 40 seconds; individual HTTP requests have a 15-second timeout. An interrupted job becomes uncertain after ten minutes; it is never automatically requeued. A network/HTTP error is conservative/uncertain because the provider may already have accepted the request. Definitive validation/rejection failures can be manually retried, up to three attempts. Accepted means provider API acceptance, not handset delivery. No delivery polling is implemented.

The local tables require prepared SQL because WordPress has no CRUD API for atomic plugin queues or these custom tables. Queue/consent reads intentionally bypass result caching so privacy revocation and order cancellation take effect in processing. Plugin Check may warn about these direct database operations and optional uninstall schema removal; document their purpose rather than hiding them under broad suppression rules.

## Privacy and reporting

Contacts store phone, keyed phone identifier, optional email, consent text/time and opt-out status. Carts store the minimal snapshot and keyed WooCommerce session association. Messages store event/object/recipient/state/error code/attempts/times, not full message text, API tokens or raw provider responses. Admin reports mask numbers. A paid purchase is attributed only to a verified recovery code and linked order; counts do not establish incremental revenue. Refund/cancellation removes it from the active recovered count.

WordPress exporters/erasers use the optional saved email; transaction-only customer logs are located using WooCommerce order CRUD. Phone-only requests can be erased by an administrator after verifying the requester. Provider-side copies and WooCommerce orders are not erased. Data retention is 7–90 days and runs daily. Order idempotency/cart-ID metadata remains with WooCommerce orders. Deactivation stops both schedulers. Uninstall removes custom tables/settings only when the existing delete-data option is enabled.

## Verification

Run `php vendor/phpunit/phpunit/phpunit -c phpunit.xml.dist` and `php vendor/squizlabs/php_codesniffer/bin/phpcs -q`. Run the integration suite only on a disposable WordPress/WooCommerce site with environment type `local`: `wp eval-file /absolute/path/tests/Integration/commerce.php`. It exercises actual WordPress storage, WooCommerce payment events and the queue with HTTP/mail intercepted. It must never be run against a real store.

The WordPress.org ZIP excludes development dependencies, tests, tooling and `.po`, `.mo`, `.l10n.php` catalogs. `python tools/build_translations.py` builds the development Persian catalog; a separate language pack can be installed under `wp-content/languages/plugins` while the plugin is still awaiting directory approval. Future WordPress.org translations should use translate.wordpress.org.
